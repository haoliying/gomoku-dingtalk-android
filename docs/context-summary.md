# 对话上下文摘要：钉钉机器人全自动五子棋联机

## 讨论脉络

### 1. 原始问题
用户询问：钉钉机器人能否发消息给另一个机器人？

### 2. 平台限制确认
经核实钉钉官方文档，结论为**不能**：
- 机器人没有"发给另一个机器人"的 API（发送目标只能是用户或群）
- 机器人回调只在**人类用户 @ 机器人**时触发，机器人发的消息不会触发另一个机器人的回调
- 单聊仅限"人—机器人"

### 3. 用户的下棋场景
两个用户各自在手机上创建机器人，同企业，交换机器人 ID，想实现机器人直接对话下棋。
- 此路不通（机器人不能互发）
- 用户进一步要求：机器人服务跑在手机上、无中心化服务器

### 4. 方案演进

| 方案 | 问题 |
|------|------|
| 机器人直接互发 | 钉钉不支持 |
| 共享后端中转 | 手机端无中心服务器，不可行 |
| 交叉单聊+人工发送 | 半自动，需人工转述走法 |
| **群消息总线+事件订阅** | ✅ 最终方案 |

### 5. 最终方案：群消息总线 + 事件订阅

**核心思路**：群充当消息总线，事件订阅当耳朵，机器人发群消息当嘴巴。

- **发送**：机器人调用 `groupMessages/send` 把结构化走法（带 `gomoku` JSON）发到群
- **接收**：应用通过事件订阅 `user_im_message_receive_group` 监听群里**所有**消息（无需 @），自动解析走法
- **自环过滤**：消息带 `from=robotCode`，接收方忽略自己发的消息
- **手机端**：Stream 模式 WebSocket 出站连接，无需公网 IP

## 关键技术决策

1. **为什么用事件订阅而非机器人回调**：机器人回调只收 @ 消息，事件订阅 `user_im_message_receive_group` 收群里全部消息
2. **为什么消息带 `from` 字段**：事件订阅会推送自己发的消息，需用 `from==robotCode` 过滤
3. **为什么用结构化 JSON 而非纯文本**：双方 App 自动解析走法，纯文本需人工判断
4. **Stream 模式双订阅**：`EVENT(*)` 收群消息事件，`CALLBACK` 兼容单聊/群 @ 场景

## 部署配置要求

1. 钉钉开放平台创建企业内部应用 + 机器人
2. 开通：机器人发群消息权限、IM 消息读取权限
3. 事件订阅勾选 `user_im_message_receive_group`
4. 建群拉入两个用户和两个机器人，获取 `openConversationId`
5. 用户授权应用读取 IM 消息
